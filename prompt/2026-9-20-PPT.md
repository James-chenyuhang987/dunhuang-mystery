3. 为方便的增加新功能

增加对比:
- 以前加一个功能：改 N 个文件 + if 分支
- 现在加一个功能：写一个插件 + 在 level 里声明

# 架构变化中遇到的问题

这套架构不是一次成型的。

在最终方案之前，我试过至少 5 种方案，每一种都在某个具体场景下崩了。

**讲这些失败，比只讲成功更有价值——每一个失败都指向了最终设计的某个决策。**

---

## 尝试 1：SendShareData

**想法**：给 EventStore 加API，通过引用传值实现共享

**崩在哪：**

| 问题       | 场景                                          |
|----------|---------------------------------------------|
| 无法确定收到   | 需要插件手动通过类似事件的机制/通过类似TCP中ACK的机制来确保收到,大大增加复杂度 |
| 共享数据不安全  | 共享数据无法确定性的触发析构,需要类似Rc的机制                    |
| 同KEY覆盖问题 | 如果共享数据的内容依赖时序,会出现UB                         |

因此,我选择不严格执行逻辑-视图分离,而是允许UI插件控制渲染,基本消除了这个需求

---

## 尝试 2：UI 插件拉起其他插件

**想法**：让 UI 插件通过 store 主动加载它依赖的插件，形成依赖图。

**崩在哪：**

- A 加载 B，B 加载 C，C 又加载 A → 循环依赖
- 加载顺序失控：谁先谁后由插件运行时决定，宿主无法编排
- dispose 顺序错乱：逆序析构失效，资源释放不可预测

**结论**：依赖应该声明，不该运行时触发加载。宿主编排，插件只声明。

---

## 尝试 3：栈（Stack）策略

**想法**：同一 key 下用数组保留每一层值，`dispose` 时弹栈回滚到上一层。

**崩在哪：**

- 栈要求每个插件的 `init` 和 `restore` 都完整对称
- 但插件作者记不住要恢复什么（`onMount` / `onUnmount` / `dispose` 三层语义）
- 忘一个状态，栈就脏了
- 除非强制所有插件都走 stack，但那属于过度设计

**结论**：单值覆盖 + 插件自己 mix，比通用栈干净。想要叠加？插件自己读当前值、mix、写回。

---

## 尝试 4：多层 Proxy

**想法**：用三层 proxy（ctx、数组、entry）拦截所有访问，隐藏内部结构。

**崩在哪：**

- 每次访问都要新建 proxy（或查 WeakMap 缓存）
- 缓存命中比直接属性访问还慢
- 缓存未命中就 `new Proxy`
- 开销不比"投影出干净视图"小，还更复杂

**结论**：用 `get` 投影 + `get_ctx_with_plugin` 零分配查找。热路径直接 `UNSAFE_get_ctx_ref`。

---

## 尝试 5：watchEffect 自动依赖追踪

**想法**：用 Vue 的响应式系统自动收集依赖，key 被清时自动清理监听器。

**崩在哪：**

- `reactive(obj)` 会递归包装整个对象树
- ctx 里全是 Three.js 重型对象：`renderer`、`camera`、`scene`
- 每帧 `position`、`matrix` 变化 → 触发 set → effect 疯狂重跑
- 第三方库（Three.js）访问的是原始引用，Proxy 拦不住，依赖收集不全

**结论**：手动声明依赖 + dispose通知

---

## 共同模式

回头看，这些失败的尝试都有同一个毛病：

**试图用框架机制解决本该由插件自己解决的问题。**

而最终的方案，把这些问题全部"消解"了——

- 需要共享数据 → UI插件，数据内部流转
- 需要依赖标识 → Symbol token，值语义
- 需要访问控制 → `get` 投影 + `unsafe` 逃生舱
- 需要依赖追踪 → 手动声明，显式清晰

**问题不是被解决的，是根本不存在的。**

---

## 一句话收尾

> 架构设计的最高境界，不是解决所有问题，而是让问题不再存在。这 7 次失败，每一次都在告诉我：能内聚的内聚，该解耦的解耦，框架只做框架的事。

# 现在的技术架构

## 本架构采用core + plugin的设计,哲学是**core仅暴露基础核心功能,一切功能都依赖于plugin提供**(单开一页讲解)

需要提到组合的思想，可以提一嘴rust
并增加类比:
微内核：Linux 内核只做调度 + IPC，驱动全在用户态
VSCode：核心 + 扩展

需要提到从微内核汲取到了一些思想

接下来是技术细节:

1. core仅提供renderer,camera等核心功能,给予插件系统极大的自由度,**为什么不将core也作为一个插件提供? - 保障哪怕插件部分出现问题仍能提供本应用的核心功能: 3D场景查看**
2. 插件分为两种类型: Renderer插件 与 UI插件,区别为UI插件在Renderer插件的基础上提供了UI相关功能,可参与用户交互
3. 本系统的core部分很简单,仅初始化THREE.JS相关环境,随后转移给plugin系统
4. 本系统的plugin部分有3个核心: usePlugins usePluginRuntime usePluginEvent

#### usePlugins
- 负责解析配置中声明使用的插件,处理插件导入与卸载,通过与导入顺序相反的卸载顺序来确保不会出现析构顺序导致的问题
- 作为全局的插件管理器，单例模式，剩余两个核心均由本核心负责协调控制
- 由于SPA导致资源管理问题十分重要,因此也负责最终的强制清理

还有一点个人觉得特别优雅(需要单独开一页讲): usePluginRuntime usePluginEvent中暴露的绝大部分方法都要求插件名作为参数传入，但是，如果让插件自行管理，那样的话不仅容易打错name导致出现漏洞，而且还会因为没做好隔离导致插件可能随时被破坏，且并不好控制插件不调用全局管理器才能调用的一些危险函数如清理整个context
因此,个人给出的方案是,在usePluginRuntime usePluginEvent中设立setPlugin方法,接受参数名称,返回允许范围内的，柯里化的内部函数,对于插件不会有任何感知,无需手动设置name,由总插件管理器传递(由于插件通过配置声明，插件管理器可以获取到其名称),通过参数名称的变量遮蔽来避免获取全局store的实例


#### usePluginRuntime
- 暴露一个runtime环境,提供一些有用的方法,如检查依赖插件是否已安装,并负责全局context对象的生命周期管理
- core最开始将其ctx传入本核心，由于引用传值，所以一切对本核心内的ctx的修改都会反映到core中
- 由usePlugins添加已导入的plugin,提供断言来进行dev期间的plugin依赖检查
- 通过Symbol来唯一标识一个CTX对象，移除时通过这个Symbol来通知usePluginEvent来卸载依赖本CTX对象的callback
- 提供setCTX,通过replace与dispose两个boolean来表示三种方式: 1. 以前的被卸载 2. 以前的被移除CTX,但plugin还可以使用以前的 3. 新加的和以前的都保留
- 一切卸载函数均保证幂等,因为可能会有double-dispose
- 本质上是lifetime的管理


#### usePluginEvent
- 通过不挂载到document的div元素作为EventListener承载容器,实现了与实际功能使用的EventListener相隔离,且可以通过DIV.remove()来移除全部监听器
- 通过命名空间隔离来实现广播与私发
- 通过CustomEvent实现,性能较自己实现事件总线更加好

|                             |
|                            通知
|                             |
----控制---> usePluginEvent <---

6. 插件系统所有内容仅300行代码左右,但带来了无与伦比的自由度,可配置性
7. 说明准确来说并不是完全的组合的方式，也含有替换的部分，如插件列表前后声明使用不同的controller，如果一昧的组合只会导致用户操作出现严重问题，所以给予插件自由度，可以选择多种方式处理前面的内容，如替换但将对象交给本插件进行管理，直接让runtime进行销毁操作等
